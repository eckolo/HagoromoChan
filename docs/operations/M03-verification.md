# M03 v2.2 実装候補の Windows 確認手順

対象: [M03](../milestones/M03.md) / [画面設計 v2.2](../design/M03-screen-design.md)

## 1. 更新と起動

v1.0のビルド成功・起動・会話表示の報告、v2.0のユーザーによる実機操作と概ねの挙動の承認を受領した。v2.1では終端の白矩形、終了後のDesktopプロセス残留が報告された。v2.2はその修正候補であり、ビルド・実機再検証が必要。

既存Desktopを右クリックの「終了」で終了する。旧版のプロセスが残る場合はHagoromoChan.Desktop.exe（または実行コマンドラインがHagoromoChan.Desktop.dllの旧Desktopプロセス）だけを確認して停止する。Relay.dll、--mcp-stdio、tunnel-clientや無関係なdotnet.exeを一括停止しない。PowerShellでリポジトリルートから実行する。未コミットの作業がある場合は保護する。Relayとtunnel-clientは稼働したままでよい。

```powershell
git status --short
git fetch origin
git switch milestone/M03-character-and-window-ui
git pull --ff-only
dotnet build .\src\HagoromoChan.Desktop --configuration Release
Start-Process .\src\HagoromoChan.Desktop\bin\Release\net10.0-windows\HagoromoChan.Desktop.exe
```

ローカル枝がまだなければ `git switch --track origin/milestone/M03-character-and-window-ui` を使用する。上記はDesktopだけをビルドする。通常の再起動ではビルドせずDesktop.exeを起動するか、ビルド済みなら `Start.ps1 -SkipBuild` を使う。全体ビルド時のファイルロックとトンネル子プロセスの再生成に関する恒久対策は[M08](../milestones/M08.md)の対象である。

新しい画像は同梱済み。以前の独自 `mascot.png` を配置している場合は、その画像が引き続き優先される。低解像度の差替え素材で同梱画像の品質を評価しないよう注意する。

## 3. 回帰検証

関連プロセスを使用中のDLLに対して全体ビルドしない。必要に応じ安全に停止した検証環境で以下を行う。

```powershell
dotnet build .\HagoromoChan.sln --configuration Release
dotnet run --project .\tests\HagoromoChan.Tests --configuration Release
```

v2.0で追加した4項目を維持し、v2.1では独立トグル状態、保持カードの差分操作、補助枠近接配置（負座標・画面端・遠隔コーナー禁止）の3項目を追加した。C#回帰テストは今回未実行。純粋ロジックテストだけでWPF実描画、ちらつき、クリック透過、フォーカスが確認済みとはしない。

## 5. 購読不成立の切り分け（観測のみ）

v2.1の実機レビューにてDotの購読登録失敗（18:28 JST、task service unexpected error）が報告された。直前のget_context成功はユーザー提供のDot報告に基づく。Relay/Contracts計11ファイルがmainと同一であり、M03の購読処理変更はない。実機のローカル到達・応答コードは未確認。

- /healthと認証付きGET /api/statusをローカルで確認し、subscribed、subscriptionExpiresAt、queuedCount、awaitingReplyCount、lastErrorを照合する。subscribedは保存済み購読のactive・期限判定であってクラウドの現在の購読一覧と同一ではない。lastErrorはoutbox配信の状態であり、直近の購読登録エラーではない。
- McpHandler.SubscribeAsyncはコールバック検証後にSaveSubscriptionする。検証失敗は-32015、別の購読先に紐付いた未回答要求が残っている場合の変更拒否は-32000（ChatStore.SaveSubscription）。コールバックは15秒、stdioのHTTP転送は25秒のタイムアウトを持つ。これらは候補であり今回の実測原因ではない。
- tunnel-clientの時刻・メソッド名・結果コードを確認する。現行Relayは購読メソッドを通常ログに記録しないため、記録なしだけでは未到達と判断しない。詳細ログが必要な場合は機密情報を出さない診断を別途検討する。既存データ・購読・認証情報を削除して回避しない。今回は通信コード変更なし。
