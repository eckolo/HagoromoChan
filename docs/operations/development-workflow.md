# 開発・進捗管理手順

## 1. 正本と責務

| 文書 | 責務 |
| --- | --- |
| [AGENTS.md](../../AGENTS.md) | 作業者全員の共通ルール |
| [ROADMAP.md](../ROADMAP.md) | 確定した ID、目的、優先順位、依存関係、作業枝 |
| [PROGRESS.md](../PROGRESS.md) | 公開済みの開発状態・実行状態・次担当の一覧 |
| [REQUIREMENTS.md](../REQUIREMENTS.md) | 全体要求・制約 |
| [ARCHITECTURE.md](../ARCHITECTURE.md) | 現行の構成と合意済み設計 |

main を統合済み成果および公開済み管理記録の正本とする。未統合の最新作業記録は各作業枝で保持する。読み手は公開記録と作業版を混同しない。会話では文書を参照し、確定した新たな決定を文書に戻す。

## 2. 状態

開発状態（成果の段階）は次のいずれか。

| 状態 | 意味・遷移条件 |
| --- | --- |
| 未着手 | 定義済みで調査・設計・実装を開始していない |
| 調査中 | 実現手段・制約・不確実性を調査中の段階 |
| 設計中 | 採用する仕様・方式・検証方法を具体化する段階 |
| 実装中 | 設計に基づく変更を作成している段階 |
| 検証中 | 変更を作成し、完了条件を照合している段階。統合候補の検証・統合待ちも含む |
| ユーザー確認待ち | 実機操作、仕様判断、権限設定などユーザーの対応が必要。具体的な依頼と再開条件を記載 |
| ブロック | 外部仕様、権限、依存、障害などにより作業不能。解除条件と担当を記載 |
| 完了 | 完了条件を満たし、main に統合し読戻し確認できた |
| 保留 | 意図的に進行を停止。理由・再開条件を記載 |

基本サイクルは、未着手 → 調査中 → 設計中 → 実装中 → 検証中 → 完了。不要な段階は理由を記して省略できる。調査・設計・実装・検証は必要に応じて前段に戻る。ユーザー確認待ち、ブロック、保留から復帰するときは再開段階を記録する。完了後の再開は理由・影響・対象 ID を明示する。

**実行状態**は上記と独立した、記録時点の実際の稼働状況とする。

| 状態 | 意味 |
| --- | --- |
| 実行中 | 当該作業を実際に実行していることを確認済み |
| 外部実行中 | 委譲先が実際に処理していることを確認済み |
| 外部回答待ち | 依頼を送付済みで、回答または処理結果が未着。実行中とは断定しない |
| 停止中 | 現在の処理は終了・中断している。次の指示やアクションを待つ場合を含む |
| 不明 | 現在の稼働状況を確認できない |

すべての進行中 ID について、次の具体的アクション、担当（AI／ユーザー／外部担当）、阻害要因、再開条件、確認済み成果を記録する。自分で進められず時間経過による解消見込みがないユーザー依存は、ユーザー確認待ちまたはブロック（ユーザー対応必要）と明記する。自動実行や外部実行の存在を推測で報告しない。

## 3. 登録・分岐

1. ユーザーと合意した ID、目的、対象・対象外、依存、完了条件を記録する。個別記録は [テンプレート](../milestones/TEMPLATE.md) を使用する。
2. ROADMAP・PROGRESS・個別記録を管理窓口で公開する。新規登録の記録だけを先に main へ入れる場合は第5節の手順を使う。
3. 現在の origin/main を確認し、そのコミットから `milestone/<ID>-<slug>` を作成する。命名例は `milestone/MGMT-01-progress-management`。ID を必ず含める。既存の同一 ID の作業枝があれば継続する。
4. 分岐元 SHA、対象枝、担当を個別記録に残す。既存の未コミット変更を捨てたり別作業の変更を含めたりしない。

Git CLI での例（実際の ID と枝名に置換する。コネクタ経由でも同じ Git 操作と履歴を維持する）。

```powershell
git fetch origin
git switch -c milestone/MGMT-01-progress-management origin/main
git push -u origin milestone/MGMT-01-progress-management
```

## 4. 並行作業・他枝の取り込み

- マイルストーン間の依存関係は ROADMAP で管理する。必要に応じて最新 main を作業枝に取り込む。
- 他の作業枝の成果が必要なら、まず main へ統合済みの成果を利用する。未統合の他枝を取り込む必要がある場合は、依存 ID、必要な範囲、対象コミット SHA、取り込み理由を記録し、差分を確認する。
- 必要なコミットを固定して merge する。枝全体の取り込みで無関係な変更が混ざる場合は取り込まない。限定コミットの cherry-pick を選ぶ場合も出所を記録し、後続統合時に重複変更・競合を検証する。
- 依存元が未完了のまま依存先の実装を main へ統合しない。先に依存元を統合する。合同統合が必要な場合は範囲・完了条件・順序を明示し承認を得る。
- 共有ブランチの履歴を書き換えない。競合は双方の意図を確認して解消する。判断できない場合は停止し、必要な担当・判断を明示する。
- 同じ ID の同じ作業枝には原則一つの作業担当を置く。同時に同じ文書・コードを更新する場合は管理窓口で調整する。

## 5. 途中経過の公開

実装途中の作業枝を main に丸ごと入れず、進捗は必要な区切りで公開する。

- 作業枝に個別記録・検証結果をコミットする。記録時点の状態と根拠となる作業コミットを残す。
- main から補助的な `record/<ID>-<slug>` を作成し、当該 ID の管理記録のみを反映する。複数回の公開は slug に区別可能な連番等を付ける。新規登録時もこの経路を利用できる。
- PROGRESS と個別文書を同時に更新する。ROADMAP は定義・依存の変更がある場合だけ、要求・設計文書は合意済み変更がある場合だけ更新する。
- 全体一覧への書込みは管理窓口で直列化する。最新 main を確認し、他 ID の行や変更を上書きしない。コード、スクリプト、依存未承認の仕様を記録更新枝へ入れない。
- 記録変更の差分・内容を照合し、main に統合して読戻す。作業枝に公開記録を取り込む際は、より新しい作業記録を失わないように調整する。
- 途中公開が不要な短い作業は、専用作業枝で記録し、完了時にまとめて統合してよい。

## 6. 完了・main への統合

1. 合意済み完了条件の全件に対し、対象版、実行環境、確認方法、結果、未確認事項を記録する。実施していない検査は成功扱いにしない。
2. 最新 main と依存の統合状況を確認して作業枝へ取り込む。競合を解消し、最終差分を確認する。無関係な変更があれば除外または統合を停止する。
3. 統合候補を必要な範囲で再検証する。コード変更の場合は関連ビルド・回帰・必要な実機確認。文書のみの場合は内容・差分・参照先の静的検証と省略理由の記録で可。
4. 個別記録・PROGRESS を整合させ、検証に用いた固定コミット SHA を記録する。検証結果の記録だけを追加した最終候補は、その追加差分を再確認する。統合結果を確定するための完了予定記録は事前に候補へ含められるが、完了の効力は main への統合・読戻し成立後にのみ生じる。候補コミット自身・将来のマージコミットの SHA を文書に書かない。
5. main への書込み直前に ref が検証時点から変わっていないことを確認する。main を更新するときは非 force を使用し、可能な場合は expected SHA による競合防止も行う。変動があれば再取り込み・再検証する。
6. マイルストーン本体は原則マージコミット（`--no-ff` 相当）で main に統合し、履歴と区切りを保持する。記録のみの短い変更は fast-forward でもよい。必要な保護や承認を迂回しない。
7. main の新 HEAD、対象枝の到達可能性、統合差分・管理記録を読戻して確認する。統合後に完了記録を確定する場合は、管理記録のみの後続コミットを使用してよい（同じ作業枝を最新 main に fast-forward して継続、または第5節の記録更新枝を利用）。完了判定できなければ報告し、必要な訂正・再検証を実施する。
8. 作業枝は原則保持する。削除、履歴書換え、force push は無断で行わない。

## 7. 中断・引き継ぎ・報告

作業が停止する場合は、実行状態を停止中等へ変更し、作業枝へのコミット（安全に保存できる範囲）と公開記録を整える。新しい会話や Work では、ID、main と作業枝の HEAD、個別記録、依存関係、未検証事項、次アクションから再開する。過去の会話を読み切れない場合でも、記録から判明する範囲を示す。

作業報告には ID・枝・コミット、実際に完了した内容、未実施の検査、阻害要因と次担当、main 統合の有無を明記する。開発状態と実行状態は別々に示す。
