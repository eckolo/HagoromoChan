# 開発・進捗管理手順

## 1. 正本と責務

| 文書 | 責務 |
| --- | --- |
| [AGENTS.md](../../AGENTS.md) | 作業者全員の共通ルール |
| [ROADMAP.md](../ROADMAP.md) | 確定した ID、目的、優先順位、依存関係、作業枝 |
| [PROGRESS.md](../PROGRESS.md) | マージ時点の確定済み状態・登録情報、作業枝を参照するための一覧 |
| [REQUIREMENTS.md](../REQUIREMENTS.md) | 全体要求・制約 |
| [ARCHITECTURE.md](../ARCHITECTURE.md) | 現行の構成と合意済み設計 |
| `docs/milestones/<ID>.md` | 個別の範囲、完了条件、最新作業・検証・統合記録 |
| [decisions](../decisions/README.md) | 重要な選択と変更理由 |
| [operations](README.md) | 開発・環境・障害対応手順 |

main を統合済み成果および確定済み管理記録の正本とする。未統合の最新作業記録は各作業枝で保持する。main だけで進行中の最新状態を断定しない。会話では文書を参照し、確定した新たな決定を文書に戻す。

## 2. 状態

開発状態（成果の段階）は次のいずれか。

| 状態 | 意味・遷移条件 |
| --- | --- |
| 未着手 | 定義済みで調査・設計・実装を開始していない |
| 調査中 | 実現手段・制約・不確実性を調査中の段階 |
| 設計中 | 採用する仕様・方式・検証方法を具体化する段階 |
| 実装中 | 設計に基づく変更を作成している段階 |
| 検証中 | 変更を作成し、完了条件を照合している段階。統合候補の検証・統合待ちも含む |
| ユーザー確認待ち | 実機操作、仕様判断、権限設定などユーザーの対応が必要。具体的な依頼と再開条件を記載 |
| ブロック | 外部仕様、権限、依存、障害などにより作業不能。解除条件と担当を記載 |
| 完了 | 完了条件を満たし、main に統合し読戻し確認できた |
| 保留 | 意図的に進行を停止。理由・再開条件を記載 |

基本サイクルは、未着手 → 調査中 → 設計中 → 実装中 → 検証中 → 完了。不要な段階は理由を記して省略できる。調査・設計・実装・検証は必要に応じて前段に戻る。ユーザー確認待ち、ブロック、保留から復帰するときは再開段階を記録する。完了後の再開は理由・影響・対象 ID を明示する。

**実行状態**は上記と独立した、記録時点の実際の稼働状況とする。

| 状態 | 意味 |
| --- | --- |
| 実行中 | 当該作業を実際に実行していることを確認済み |
| 外部実行中 | 委譲先が実際に処理していることを確認済み |
| 外部回答待ち | 依頼を送付済みで、回答または処理結果が未着。実行中とは断定しない |
| 停止中 | 現在の処理は終了・中断している。次の指示やアクションを待つ場合を含む |
| 不明 | 現在の稼働状況を確認できない |

すべての進行中 ID について、次の具体的アクション、担当（AI／ユーザー／外部担当）、阻害要因、再開条件、確認済み成果を記録する。自分で進められず時間経過による解消見込みがないユーザー依存は、ユーザー確認待ちまたはブロック（ユーザー対応必要）と明記する。自動実行や外部実行の存在を推測で報告しない。

## 3. 登録・分岐

1. ユーザーと合意した目的、対象・対象外、依存、完了条件を記録する。ID は管理窓口で直列に予約する。main の ROADMAP・個別記録・登録履歴、作業枝、未登録の確保済み予約を照合し、管理系・アプリ系を通した確保済み最大番号の次を採る。予約時に ID・名称・担当・予定枝を記録し、登録済み・予約済みの番号は完了・中止等でも再利用しない。欠番を詰めない。個別記録は [テンプレート](../milestones/TEMPLATE.md) を使用する。
2. ROADMAP・PROGRESS・個別記録を管理系マイルストーンの専用枝で登録し、第6節の規則で main にマージする。登録時点ではアプリ作業枝の予定名を記載し、実際の着手時に枝を作成する。
3. 現在の origin/main を確認し、そのコミットから `milestone/<ID>-<slug>` を作成する。命名例は `milestone/MGMT-01-progress-management`。ID を必ず含める。既存の同一 ID の作業枝があれば継続する。
4. 分岐元 SHA、対象枝、担当を個別記録に残す。既存の未コミット変更を捨てたり別作業の変更を含めたりしない。

Git CLI での例（実際の ID と枝名に置換する。コネクタ経由でも同じ Git 操作と履歴を維持する）。

```powershell
git fetch origin
git switch -c milestone/MGMT-01-progress-management origin/main
git push -u origin milestone/MGMT-01-progress-management
```

## 4. 並行作業・他枝の取り込み

- マイルストーン間の依存関係は ROADMAP で管理する。必要に応じて最新 main を作業枝に取り込む。
- 他の作業枝の成果が必要なら、まず main へ統合済みの成果を利用する。未統合の他枝を取り込む必要がある場合は、依存 ID、必要な範囲、対象コミット SHA、取り込み理由を記録し、差分を確認する。
- 必要なコミットを固定して merge する。枝全体の取り込みで無関係な変更が混ざる場合は取り込まない。限定コミットの cherry-pick を選ぶ場合も出所を記録し、後続統合時に重複変更・競合を検証する。
- 依存元が未完了のまま依存先の実装を main へ統合しない。先に依存元を統合する。合同統合が必要な場合は範囲・完了条件・順序を明示し承認を得る。
- 共有ブランチの履歴を書き換えない。競合は双方の意図を確認して解消する。判断できない場合は停止し、必要な担当・判断を明示する。
- 同じ ID の同じ作業枝には原則一つの作業担当を置く。同時に同じ文書・コードを更新する場合は管理窓口で調整する。

## 5. 途中経過と全体進捗の把握

main の履歴に現れるマージを、マイルストーンの完了点として識別できるようにする。途中経過だけを main に反映しない。

- 各作業枝の `docs/milestones/<ID>.md` を、当該 ID の未統合の最新作業記録とする。作業の区切りで状態、担当、阻害要因、再開条件、検証結果をコミットする。
- 全体の状況を確認するときは main の ROADMAP と PROGRESS を起点に、予定名の作業枝の有無、HEAD、個別記録、main へのマージ履歴を照合する。未作成なら main の登録情報を参照する。枝の存在だけで実行中と判断しない。
- main の PROGRESS はマージ時点の確定記録であり、リアルタイムの進捗一覧ではない。全体報告は各作業枝を読み取って集約する（main への途中記録コミットは不要）。
- 完了時の統合候補で対象 ID の PROGRESS と個別文書を整合させる。最新 main の他 ID の行を維持する。ROADMAP は合意済みの定義・依存変更がある場合だけ、要求・設計文書は合意済みの変更がある場合だけ更新する。
- 新規登録、方針変更、統合後の記録訂正などを単独で main に反映する必要がある場合も、目的と完了条件を持つ管理系マイルストーン（MGMT 系）として扱い、専用枝をマージする。途中経過の写しを目的とした旧 `record/` 運用は廃止する。

作業分解と成果物分解は一対一に対応させない。一つの作業が複数の機能・テストを変える場合も、異なる作業が同じ部品・検査を育てる場合もある。機能とテストは、完了後も残る利用者の操作・契約・検証対象で命名し、部品の責務や検証する振る舞いに沿って構成する。例えば履歴の描画検査は `WindowsLayout.RenderedHistory` のように表し、診断ログには対象と操作を出す。マイルストーンとの対応は個別記録に残し、番号や作業段階を成果物へ埋め込まない。

通常の回帰検査は共通の起動手順で実行する。テスト全体は失敗を集計し、独立して実行できる後続検査を続ける。個別のマイルストーン専用の起動手順や、診断のためのケース分割は原則増やさない。通常の検査とログで原因を絞れない場合の最終手段とし、常設の手順にはしない。

## 6. 完了・main への統合

1. 合意済み完了条件の全件に対し、対象版、実行環境、確認方法、結果、未確認事項を記録する。実施していない検査は成功扱いにしない。
2. 最新 main と依存の統合状況を確認して作業枝へ取り込む。競合を解消し、最終差分を確認する。無関係な変更があれば除外または統合を停止する。
3. 統合候補を必要な範囲で再検証する。コード変更の場合は関連ビルド・回帰・必要な実機確認。文書のみの場合は内容・差分・参照先の静的検証と省略理由の記録で可。
4. 作業枝で個別記録・PROGRESS を整合させ、完了予定記録、検証に用いた固定コミット SHA を含む最終候補を作る。追加記録の差分も確認する。文書上の「完了」は当該マイルストーンの完了マージが main に成立している場合のみ有効であり、作業枝だけを読む場合は未統合の完了候補として扱う。候補自身・将来のマージコミットの SHA を文書に書かない。
5. main への書込み直前に ref が検証時点から変わっていないことを確認する。main を更新するときは非 force を使用し、可能な場合は expected SHA による競合防止も行う。変動があれば再取り込み・再検証する。
6. main への反映はすべて、完了したマイルストーンの専用枝の2親マージコミット（`--no-ff` 相当）で行う。第1親は直前の main HEAD、第2親は検証した作業枝 HEAD とし、マージメッセージに ID と名称を含める。管理文書だけでも同じ。main への直接コミット、fast-forward、squash、rebase 統合は行わない。例外には事前のユーザー明示承認が必要。必要な保護や承認を迂回しない。
7. main の新 HEAD、マージの親、候補とのツリー一致、管理記録を読戻して確認し、マージ SHA と結果を報告する。マージ成立・読戻し前に完了と報告しない。完了確認だけのために main へ後続コミットしない。マージ後に訂正が必要な場合は新たな管理系マイルストーン等で修正する。
8. 完了した作業枝はマージ時の第2親の位置で保持し、完了マージ後の main へ移動しない。削除、履歴書換え、force push は無断で行わない。

Git CLI での統合例（作業枝に最新 main を取り込み、最終候補を検証してから実行する）。

```powershell
git fetch origin
git switch main
git pull --ff-only origin main
git merge --no-ff milestone/MGMT-02-merge-policy-and-roadmap -m "Merge milestone MGMT-02: Merge policy and roadmap"
git push origin main
```

`pull --ff-only` はローカル main を既存の origin/main と同期する操作であり、作業枝を main に fast-forward 統合することではない。統合前にローカル main が origin/main と一致すること、作業枝 HEAD が検証済み SHA と一致することを確認する。`git log --first-parent --merges main --oneline` で完了マージを確認できる。コネクタ経由では同じ親構造・ツリーを確認し、expected SHA と非 force で ref を更新する。

## 7. 中断・引き継ぎ・報告

作業が停止する場合は、実行状態を停止中等へ変更し、作業枝の個別記録にコミットする（安全に保存できる範囲）。main を途中更新しない。新しい会話や Work では、ID、main と作業枝の HEAD、個別記録、依存関係、未検証事項、次アクションから再開する。過去の会話を読み切れない場合でも、記録から判明する範囲を示す。

作業報告には ID・枝・コミット、実際に完了した内容、未実施の検査、阻害要因と次担当、main 統合の有無を明記する。開発状態と実行状態は別々に示す。
