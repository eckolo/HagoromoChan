# M06 通信状態の管理・障害復旧

## 定義

- ID: M06
- 優先度: 中（2026-11-25、低→高→中。M08で緊急性が低下したことを踏まえたユーザー指示）
- 目的: 現在の接続・送受信状態を適切に区別して処理停止箇所を把握できるようにし、購読不成立、配送済み未回答、接続障害からデータを保護したまま安全に復旧できるようにする。
- 対象範囲（初期案）: ローカル中継、トンネル、購読、イベント配信、返信待ち・受信、未読回答などの観測・表示・診断。購読の成立・期限・更新管理、未回答要求の識別・明示的な処理打切り、冪等性を維持した回復操作、元購読先が利用不能な場合の安全な再登録、機密情報を除いた診断記録。
- 対象外: 観測できない Dot 内部状態を実測とすること、通信方式の未承認の大幅変更、無断での DB・購読・履歴削除や別購読先への要求転送、M08 の OS プロセス起動／停止・自動起動管理、M04/M05 の新規会話経路、M14 の閲覧操作による新着解除規則の変更。
- 依存 ID: M03 の基本 UI（ユーザー受入に基づき完了）。M08 との技術依存・境界は設計時に確認。
- 着手条件: M03・M08完了後。中優先度とし、M04の高優先度・M09の早期並行着手候補を先に検討する。M06の範囲は維持し、着手指示後に進める。
- 作業ブランチ（予定）: `milestone/M06-connection-status`
- 分岐元 main SHA: 未着手・枝未作成。
- 担当: AI（着手指示後）。
- 根拠: 2026-11-25 のユーザー提示一覧、および購読不成立・未回答残留を受けた範囲拡張と優先度高への変更指示。詳細仕様・完了条件は着手時に確定する。

2026-11-25 のユーザー報告・読み取り専用の実機確認では、ローカル購読の有効期限内判定は True、配送待ち0、配送済み未回答3、配信エラー記録なし。get_context の成功報告がある一方、購読再登録でクラウド側の task service unexpected error が報告された。HTTP受理はDotによる実際の実行開始・回答生成を証明しない。登録要求のローカル到達、JSON-RPC結果コード、新旧コールバックの同一性は未確認。M03 と main の Relay/Contracts 11ファイルが同一であったことは静的に確認済みで、今回の UI 変更を通信障害の原因と断定しない。

既存コードの候補: コールバック検証失敗（-32015）、別購読先に紐付く未回答が残る場合の変更拒否（-32000）、入力検証や転送タイムアウト。15秒のコールバック検証、25秒のstdio転送タイムアウトがあるが、今回の発生箇所を確定したものではない。最新の状態は再観測する。診断では時刻・メソッド名・安全な段階／結果コードを記録し、URL・シークレット・トークン・本文を不用意に保存・出力しない。

追記（MGMT-15）: 上記は障害発生時点の記録。後続のデバッグログと公式tunnel-client v0.0.21の実装を照合し、購読要求が初期化ガードの409 / -32002で拒否されたことを特定。初期化完了通知補完 `--mcp.stdio-send-initialized-notification=true` によりユーザーが購読成功を報告した。M08で同設定を管理起動に組み込み、stdioパスのエスケープを修正した後、v1.0.3の管理起動・会話往復、v1.0.4の全般的受入を確認した（[M08](M08.md)）。従来の緊急の障害を現在も継続しているとは扱わない。未回答要求の扱い・安全な復旧・長期購読・観測可能性の課題は残す。M06自体は未着手である。

### M04のツール更新後に発生した購読元接続の不一致（2026-11-25～26、MGMT-16）

M04 v1.0実装候補（作業枝固定版 `4e63273869188e629683092a7c090b4e0b5eca06`）のWindows実機検証で発生した。M04を完了・統合済みとは扱わない。

**受領した事実・確認範囲**

- Relayのtools/listでget_context、reply、send_messageの3ツールを確認。ChatGPT側のツール更新後、send_messageが認識され、DotからWindowsへの独立発言が届いた。
- Windowsからの返答送信後、管理・Relay・Tunnelは稼働／準備完了、ローカル購読は有効、送信待ち0・返信待ち1と表示された。現行コードのMarkDeliveredはWebhook送信成功後に実行されるため、ローカル記録からHTTP受理済みと判断できる。ただし実際のHTTP応答コード・クラウド内部配送ログは未取得であり、Dotの実行を証明しない。
- Dot側の確認報告では、対象request_idのget_contextによる本文と能動発言への関連付けの取得に成功。対応するmessage.createdの受信記録を確認できず、既存タスクの最終実行は11/25 20:21:27 JST（今回の発言23:22:33 JSTより前）。同一request_idへの手動replyは成功した。
- 既存イベント購読の更新を試みると `Use the connector connection that created this subscription.` により拒否された。Dot側では旧タスクが有効。現在の接続から元の接続が作成した購読を更新できないという報告を受領。実行ログとバッチ処理設定は取得不能。「最大6回／時」は実行回数上限であり、バッチ設定の確認結果ではない。
- ツール更新前後の接続識別子、接続の変化が起きた時点と原因、旧購読にHTTP受理されたイベントの実際の行先、旧タスクの停止・新購読成立・自動応答復旧は未確認。更新操作が接続を変更したと断定しない。自動応答停止と購読更新拒否の因果関係も未確定。M04のDB・受信処理の破損を示す証拠はない。

**M06で必ず扱う追加の設計・検証課題**

- MCPツール定義の更新、再接続、接続の失効・置換を契機とする購読互換性を確認する。接続の所有関係（作成元接続と現在接続）、クラウド購読／イベントタスクの有効性、ローカル保存済み購読、Webhook HTTP受理、タスク実行・最終実行、返信到着を別状態として定義する。アクセス可能な識別情報のみ用い、取得不能なら不明と表示する。
- 更新前後の健全性確認手順を整備する。tools/list、既存ツールの個別実行、ローカル状態、取得可能なタスク状態、無害なmessage.createdテストと同一request_idのreply到着を照合し、ツール利用可能／購読ローカル有効だけで正常と判定しない。実行遅延・実行回数上限・バッチ設定・未実行・接続不一致を観測範囲で区別する。
- 上記拒否エラーを明示的な復旧分岐に含める。まず作成元の接続が利用可能ならその接続での購読更新を検討する。利用不能なら、旧タスクの指示・対象チャンネル・権限を保存し、利用者承認の下で旧タスクを無効化・停止確認してから現在接続で購読を登録する。タスク停止と購読解除は別処理。旧タスク停止を確認できない、元の購読を安全に扱えない、新登録の成否が不明という場合は新規の重複登録や無条件再試行をしない。利用可能な管理操作と外部制約に従い、手動介入が必要なら明示する。
- 切替前に送信待ち／返信待ちと元の購読先への紐付けを確認する。未回答がある場合は元のrequest_idでの確認・回答回収、または利用者が明示的に承認する打切り等の設計済みの処理を経る。既存の購読先変更ガードを解除して別購読先へ無断再配送しない。履歴・DB・ID・秘密情報の保護、遅延返信、切替途中の失敗、再起動・重複イベント・冪等性を検証する。
- 新購読の有効表示だけで復旧とせず、登録後の新規Windows発言でイベント起動・get_context・replyの往復と、旧タスクの重複動作がないことを確認する。プラグインの削除・再作成やDB初期化を通常の復旧手段にしない。診断記録に本文・トークン・署名秘密・生のコールバックURLを保存しない。

状態整理の対象:
- ローカルHTTP接続、stdio／トンネル疎通、クラウド購読の状態とローカル保存済み購読の有効期限を区別する。未観測は不明とする。
- 未送信／配送待ち／HTTP受理済み／回答未着／回答受信／失敗／利用者が明示した打切り等の意味を整理する。内部実行状態は実測できる場合だけ表示する。
- 配送済み未回答を識別し、同じ要求を再実行して重複作業を起こさないよう、手動の確認・回答回収・再処理・キャンセルの条件を設計する。別購読先への切替と既存要求の扱いを明示し、元のデータ・履歴・ID・冪等性を保持する。
- 購読失敗時に診断と安全な復旧手段を用意する。キャンセルや再登録による旧要求の移行・遅延返信の処理を設計・検証し、既存の安全制約を理由なしに解除しない。
- M03の状態枠の「新着 N」はローカルの未読回答ID数であり、表示・閉じる・新着ボタンでは減らず、個別の✓で既読となる。ユーザーから分かりにくい旨の質問あり。通信上の未回答とは別の状態である。ユーザーの追加指示により「新着」の表記を維持する。履歴窓のアクティブ化・履歴スクロールによる新着解除と個別✓操作の改善は低優先度の [M14](M14.md) に分離する。M06では通信上の未回答と受信済み新着を混同させない状態定義・表示を扱い、自動既読規則の変更を完了条件としない。
